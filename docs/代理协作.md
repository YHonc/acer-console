## 分工

| 环节 | 执行者 | 说明 |
|---|---|---|
| 规划、拆任务、写契约 | 主代理与用户 | 契约文档（如 `docs/DC-IPC协议-v1.md`）是实现与审查的唯一依据 |
| 前端设计、预览稿、日常 UI 修改 | 主代理，在主对话中完成 | 用户偏好：UI 不交给子代理 |

| 证据核对、偏移量复现、审查初筛 | `group/deepseek-v4.1-flash` 或 `group/gpt-6-luna` | 便宜、边界清楚、结果可核实；只作为强审查之前的初筛，不能当作合并结论 |

## 一个功能的流程

1. **契约**：主代理写明范围、接口和完成标准，用户确认。
2. **实现**：`bash work/prompts/run.sh <任务> cpa/gpt-6.1-sol allow <目录> <提示>.md _write.md <worktree名>`，在 worktree 中提交，不 push，不合并。
3. **复验**：主代理在 worktree 中本地复跑测试；数字与代理自报不一致时，以复跑结果为准。
4. **审查**：强模型审查。结论为阻断或应修时，派 `<任务>-fix` 回到同一个 worktree 修复，再复审，直到结论为“建议合并”。
5. **合并**：用 `--no-ff` 合并到主分支，合并后再跑一遍完整验证。
6. **收尾**：在 `work/prompts/runs.md` 记一行（任务、模型、权限、提交、测试数、结论）；把 `work/<任务>/report.md` 改名为 `codex-reply.md` 后提交；更新 `当前进度.md` 与 HANDOFF。

## 委派约定

- 会话标题由 `run.sh` 自动设为 `逆向宏碁·<任务>·<模型>`，便于在 codeg 中查找。
- 只读任务附 `_common.md`，写代码任务附 `_write.md`，两者都禁止操作硬件。
- 提示中写清改动范围、契约位置、完成标准，以及最终回复需包含的内容（文件清单、提交哈希、测试命令与通过数、未完成项、契约问题）。
- 前台运行，不用 `--detach`：它的结果只保留 30 分钟，曾因此丢失过结果。
- 写入 D 盘 Device Center 仓库的任务，在该仓库运行；它的 0.1.1 改动尚未提交到主分支，分支选择见 HANDOFF。
