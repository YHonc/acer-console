# 功能验证路线（2026-11-07）

> 来源：E1 起草（deepseek-v4.1-flash，2026-11-07），主代理审定。审定时的修改：措辞修正；DC 项注明适用前提；开发者 mock 测试移出用户测试单。

> 适用对象：PHN16-71、BIOS V1.18 的 11-07 新整合包。阶段 4 的 UI、Device Center 分支和最终打包尚需集成；若包中缺少对应入口，记录“未实现/未集成交付”，不能记通过。
>
> 证据等级：**事实**有文件行号、偏移或 RVA；**推断**由已见实现推导；**未验证**尚无本机物理或端到端证据。任何硬件写入都必须由用户逐项明确批准，读回成功不能替代风扇、灯光、充电或供电的物理效果。

## 1. 性能模式（含 Eco 6 与 DC 规则缺口）

**现状证据**

- **事实**：官方能力包含 `[0,1,4,5,6]`，AC 下 Quiet/Balanced/Performance/Turbo 已实测；Eco/DC 尚未验收。`docs/official-feature-coverage.md:141-143`。
- **事实**：当前正常 Verified 白名单只允许 Quiet/Balanced/Performance/Turbo，Eco 被排除；模式写入要求 AC 且电量不低于 40%。`crates/acer-device/src/lib.rs:29-31`、`crates/acer-device/src/platform.rs:138-142`、`crates/acer-protocol/src/lib.rs:216-220`。
- **事实**：官方 Eco 的硬件模式编码为 `6`，输入形如 `0x060B`；完整官方 Eco 还包含音量、亮度、WhisperMode、灯光和风扇策略，不能等同于当前 `SetProfile`。`work/R1/report.md:46-84`、`work/W1/report.md:18-41`。
- **事实**：电源规则的 DC 已验证目标目前为空，界面可只剩“不切换”。`apps/desktop/src-tauri/src/rules_runtime.rs:13-16`、`apps/desktop/src/lib/PowerRules.svelte:80-85`。
- **事实**：正式 UI 会在设备能力声明 Eco 时显示节能草稿，但后端 Verified 仍会拒绝；这是当前闭合缺口。`apps/desktop/src/App.svelte:1153-1185`。
- **推断**：当前安全验收应先证明 Eco/DC 控件会失败关闭且不产生虚假成功；实际写入 Eco 及 DC 自动切换应另立实现和授权。
- **未验证**：Eco 对 PL、GPU、风扇和亮度的本机物理效果；AC/DC 往返及 `LastOpMode` 策略。

**自动可检（无硬件）**

- 已可做：白名单、AC/40% 门禁、Eco 拒绝、DC 目标为空和只显示“不切换”的单元/静态检查。
- 应补充：模拟能力同时含 Eco 时，确认 UI 不虚报“已应用”，后端拒绝原因可读，失败不会写入其他模式。

**需用户逐项批准的写入**

- 需用户逐项批准：Quiet/Balanced/Performance/Turbo 的每次模式应用，以及任何后续 Eco 写入。
- 当前包不应仅因点击按钮就触发 Eco 写入；若观察到实际写入，立刻停止该项并记录为门禁缺陷。

**用户实测步骤**

1. 保存当前 AC 模式、电量、电源状态和原始风扇模式。
2. AC 且电量至少 40% 时，逐次切换四个已支持模式，每次等待独立读回。
3. 若节能草稿可见，确认应用被明确拒绝或不可用，不得显示读回成功。
4. 打开电源规则，确认电池目标没有未验证选项；本阶段不要求拔电。
5. 恢复原 AC 模式并再次读回。

**通过标准**

- 四个已支持模式与请求一致；草稿、当前值和未知状态分开。
- Eco 不产生虚假成功；DC 选项不伪造已验证模式。
- 用户能观察到的性能变化可另行记录，但读回只证明固件接受，不能证明实际功耗策略。

**恢复步骤**

- 重新选择步骤 1 的模式并读回；拒绝或未确认时使用官方 PredatorSense 恢复。任何真实 Eco/DC 验证必须另行恢复原 AC/DC 状态。

## 2. 风扇 Auto/Max/Custom

**现状证据**

- **事实**：UI 提供“自动/最大/自定义”，CPU 与 GPU 分别输入百分比，未知目标不以读数冒充。`apps/desktop/src/lib/FanControls.svelte:22-41,112-148`。
- **事实**：Auto、Max 和 Custom 三步编码分别闭合到 `SetGamingFanBehavior`/`SetGamingFanSpeed`。`work/R1/report.md:144-172`。
- **事实**：Auto/Max 已有实机记录；Custom 只有 70% 点有物理证据，0/100 未验收。`docs/official-feature-coverage.md:142-143`。
- **事实**：同类实测提示风扇需约 8–10 秒才能稳定，短采样容易误判。`work/feature-route-research.md:31,38`。
- **未验证**：11-07 新包在真实读数下四张状态、听感和 RPM 响应是否完整一致。

**自动可检（无硬件）**

- 可做：编码、范围、写后读回、失败恢复、未知值显示—、最大/自动按钮和资源锁测试。
- 不做：代理读取 RPM 或调用 WMI/HID。

**需用户逐项批准的写入**

- 需用户逐项批准：Auto、Max、Custom 40/70，以及最终恢复 Auto。
- 0%、100% 和强杀进程后的恢复不属于本次常规测试。

**用户实测步骤**

1. 保存当前模式、CPU/GPU 目标及 RPM 基线。
2. 应用 Auto，等待至少 10 秒后记录读回、RPM、风声和风量。
3. 应用 Max，等待至少 10 秒后比较物理变化。
4. 应用 Custom CPU 40%、GPU 70%，等待稳定后记录读回和物理响应。
5. 应用 Auto 恢复。

**通过标准**

- 三种模式均无虚假成功；Custom 两个目标与读回一致。
- 至少 Max 与其余模式对应用户可感知的物理变化；仅数值读回变化不算完全通过。

**恢复步骤**

- 点击 Auto 并独立读回；失败时使用官方 PredatorSense 恢复 Auto，关闭本控制台后再次确认。

## 3. 温控曲线

**现状证据**

- **事实**：曲线由主机软件调节；每条 2–16 点，温度递增、百分比不递减，有滞回，未提供默认曲线，停止时恢复 Auto。`docs/温控候选版使用与测试.md:8-19`、`apps/desktop/src/lib/ThermalControls.svelte:127-202`。
- **事实**：它不是固件 FanTable；传感器失效、外部改写、AC 丢失会停止并尝试恢复 Auto。`docs/温控候选版使用与测试.md:15-20`。
- **事实**：强杀 helper、系统崩溃或 WMI 永久阻塞后的恢复无法保证。`docs/温控候选版使用与测试.md:18-19`。
- **未验证**：11-07 包的真实启动、目标变化、物理 RPM、停止读回和睡眠恢复。

**自动可检（无硬件）**

- 曲线约束、持久化但不自动启动、插值/滞回、传感器未知、写失败、停止和重试路径可离线测试。

**需用户逐项批准的写入**

- 需用户逐项批准：保存后启动曲线、每次目标占空比控制、停止并恢复 Auto。
- 睡眠、强杀 helper 和长时间热负荷测试需再单独批准。

**用户实测步骤**

1. 保存原风扇模式，记录当前 CPU/GPU 温度和 RPM；仅在 AC 下测试。
2. 在 CPU/GPU 曲线各填写两点，保存并确认状态仍为“未运行”，不预填推荐点。
3. 经批准启动，等待至少 10 秒，记录目标、温度、RPM 与物理响应；不要用单次采样判断。
4. 运行中尝试修改性能模式或普通风扇模式，确认被明确阻止。
5. 停止并恢复 Auto，独立读回自动模式。

**通过标准**

- 曲线启动前无隐藏点；运行中目标随真实温度变化，未知温度不被当成 0°C。
- 停止后 Auto 有独立读回，且有可观察的物理恢复；出现“恢复未确认”不能记通过。

**恢复步骤**

- 使用“停止并恢复自动”或“重试恢复自动”；仍失败时先在官方 PredatorSense 恢复 Auto，再明确记录本控制台结果未知。

## 4. 四区灯光与灯效（含 RBG 通道顺序）

**现状证据**

- **事实**：静态 UI 明确四区从左到右，亮度 0–100，草稿色块不代表当前灯色。`apps/desktop/src/lib/LightingControls.svelte:75-109`。
- **事实**：动态 UI 包含呼吸、霓虹、波浪、渐变、缩放、流星、闪烁，以及速度、亮度、方向、单色和恢复上一步。`apps/desktop/src/lib/LightingEffects.svelte:23-52,119-185`。
- **事实**：PHN16-71 外部报告出现过实际颜色呈 RBG 顺序，因此必须分别用纯红、纯绿、纯蓝和四区边界验证。`work/feature-route-research.md:58-71`。
- **事实**：恢复使用设备读取组件持有的上一步真实灯光，属于会话恢复能力。`apps/desktop/src/lib/LightingEffects.svelte:180-185`。
- **未验证**：11-07 新包七种灯效、方向、亮度和四区边界的最终物理表现。

**自动可检（无硬件）**

- 可检：四区长度/颜色格式、亮度范围、能力门禁、读写互斥、写后读回、冲突提示和恢复请求是否发出。

**需用户逐项批准的写入**

- 需用户逐项批准：每次静态颜色/亮度应用、每种动态灯效、方向和恢复上一步。
- 测试前必须抄录或截图保存当前灯效、亮度、四区颜色和方向。

**用户实测步骤**

1. 保存原灯光配置，选择“常亮·四区静态”。
2. 经批准将四区全部设为纯红 100%，再全部纯绿、全部纯蓝，逐次应用并记录物理颜色。
3. 设置 1 区红、2 区绿、3 区蓝、4 区红，确认分区边界及左右顺序。
4. 逐项测试七种动态灯效；波浪/渐变另测方向，速度/亮度选择可观察差异值。
5. 使用“恢复上一步灯光”，核对读回和物理效果。

**通过标准**

- 四区边界、红/绿/蓝、亮度和七种动画均有物理证据；不能只用色块或设备读回。
- 若绿显示为蓝、蓝显示为绿，明确记录为 RBG 通道顺序缺陷，不能记通过。

**恢复步骤**

- 先点“恢复上一步灯光”；失败后按步骤 1 的手工记录重设全部区域、亮度、灯效、速度和方向，再由官方 PredatorSense 作为后备。

## 5. 80% 充电保护

**现状证据**

- **事实**：当前调用为 `BatteryControl.SetBatteryHealthControl`，`uBatteryNo=1`、`uFunctionMask=1`，官方 Optimized 固定限制到 80%，没有百分比输入。`work/charge-limit/report.md:6-11`。
- **事实**：项目写后校验更严格，要求返回码、bit1 支持和其他状态符合预期。`work/charge-limit/report.md:6`。
- **事实**：现有记录证明状态往返与恢复，没有证明电池实际停在 80%。`docs/official-feature-coverage.md:148`。
- **未验证**：服务停止、重启或断电后的保持性，以及本机可调 Boundary。

**自动可检（无硬件）**

- 可检：请求字段、ACK、完整状态读回、失败恢复和“未知”处理；不能自动证明电池停止充电。

**需用户逐项批准的写入**

- 需用户逐项批准：开启或关闭限制，以及最终恢复原状态。
- 为避免长时间测试，仅在 AC 接电且电量不高于约 75% 时安排；不要在低电量出差场景测试。

**用户实测步骤**

1. 记录原保护状态、电量、AC 状态及当前充电情况。
2. 经批准开启保护，读回确认已开启。
3. 让电池自然充电，观察系统或官方组件的充电状态及最终停留区间。
4. 完成后恢复原状态并再次读回。

**通过标准**

- 读回可证明设置被接受；只有实际停止在约 80% 附近且未继续正常充至满电，才算物理通过。
- 短暂停在 80% 后继续充电、远超 80% 或状态读回与请求不符均记失败。

**恢复步骤**

- 关闭限制并独立读回；失败时由官方 PredatorSense/Acer Care 恢复，保留原状态和电量记录。

## 6. USB 关机供电

**现状证据**

- **事实**：USB 关机供电与充电保护独立，开关和 10/20 截止阈值是独立状态。`apps/desktop/src/lib/UsbCharge.svelte:127-148`、`work/charge-limit/report.md:11`。
- **事实**：现有正式 UI 开关/阈值往返和恢复已有记录，实际关机供电未验。`docs/official-feature-coverage.md:156`。
- **事实**：UI 明确“低于截止电量停止关机供电”，写后执行独立读取确认。`apps/desktop/src/lib/UsbCharge.svelte:130-147`。
- **未验证**：具体 USB 端口、设备、电池接近阈值时的截止行为，以及关机后持续时间。

**自动可检（无硬件）**

- 可检：开关与阈值不被混写、参数校验、ACK/完整读回、冲突提示和恢复请求。

**需用户逐项批准的写入**

- 需用户逐项批准：启用/关闭 USB 关机供电和截止阈值修改。
- 测试使用已知安全、非关键设备，并确保电池高于所选阈值。

**用户实测步骤**

1. 记录原开关、阈值、电池电量和准备使用的 USB 设备/端口。
2. 经批准启用 20% 并应用，确认独立读回。
3. 执行完整关机，不进入睡眠或重启；插入测试设备并观察是否供电。
4. 开机后恢复原开关和阈值，再读回。

**通过标准**

- 设置读回只算配置成功；关机后设备实际获得供电才通过。
- 低电量阈值截止、长时间供电和不同端口需另测，不能由本次开关测试推定。

**恢复步骤**

- 在本控制台恢复原开关和阈值；若不可用，使用官方 PredatorSense 的关机 USB 充电页面恢复并再次读取。

## 7. 模式键事件采集（只记录，不实现）

**现状证据**

- **事实**：官方路径为 `ROOT\WMI` 的 `APGeEvent`；首字节 `7` 进入模式键分支，第二字节只接受 `4/5`。`work/R1/report.md:92-105,198-203`。
- **事实**：PHN16-71、BIOS V1.18 的外部实机样本为 `function=0x7 key_num=0x5 device_state=0x1`。`work/W1/report.md:80-84`。
- **事实**：第二字节 `4/5` 的按下、释放或其他语义尚未确定。`work/R1/report.md:101-107`。
- **未找到**：属于模式键的独立 HID report ID、普通 `KEY_PROG` 映射和 ACPI/EC 前置触发链。
- **事实**：当前产品未实现模式键监听；校准监听只接受其自己的事件类型。`work/R1/report.md:180-183`。

**自动可检（无硬件）**

- 当前只能做事件解析器的离线测试；真实字节必须先采集，不能在无样本时编造映射。

**需用户逐项批准的写入**

- 无硬件写入。采集只订阅 `APGeEvent`、记录时间和 `EventDetail`，不得触发任何模式切换。
- 若采集器要求管理员权限或启动新服务，应由用户确认；本次不实现产品监听器。

**用户实测步骤**

1. 由用户在提升权限的 PowerShell 中订阅只读 `SELECT EventDetail FROM APGeEvent`。
2. 先记录至少 30 秒空闲样本，再分别做单次短按、长按、释放、连续两次按键，并在日志中标注动作。
3. 保存原始字节、长度、接收时间、重复次数和是否伴随其他事件；不能只保存解码后的名称。
4. 只把 `EventDetail[0]=7` 且 `[1]=4/5` 的分支纳入候选样本，并保留未匹配样本供排除。
5. 结束订阅，确认没有模式变化、服务操作或硬件写入。

**通过标准**

- 每个物理动作能够重复得到稳定原始样本，并能区分至少 `7/4`、`7/5`、重复帧和无关事件。
- 通过只代表采集完成；按键语义、AC/DC 策略和自动切换仍为未验证。

**恢复步骤**

- 模式键未执行动作，不需要恢复；若官方设置被其他程序改变，使用官方界面恢复。删除测试订阅不涉及产品功能。
