# 路线规划（2026-11-08）

本文规划 v0.1.0 发布之后的功能推进顺序。每个阶段都写明负责人、依赖和完成标准；完成标准沿用 AGENTS.md 的“验证”一节，凡涉及硬件写入的地方，实机验收由用户执行，代理只做构建、离线测试和浏览器检查。

## 排序原则

1. **先把已写好的东西验收掉，再写新功能。** 现有功能中“待验收”的比例偏高，新功能会进一步扩大回归面。
2. **只读先于写入**，写入先做“写后读回 + 恢复”，再开放界面。
3. 一个阶段只开一个涉及硬件写入的方向，避免实测时问题互相干扰。

## 阶段一：v0.1.0 实机验收（用户执行，约 1–2 天）

| 项 | 内容 | 依赖 |
|---|---|---|
| 1.1 | 发布包启动、托盘、自启动、退出恢复 | Release `v0.1.0` |
| 1.2 | 11-08 界面：侧栏宽度/边距与拖动、图标、滑块填充 | 同上 |
| 1.3 | 风扇 Auto/Max/Custom、性能模式、灯光在新包中的回归 | 同上 |
| 1.4 | Device Center：模块发现与信任、握手、外设读写与补读、挂灯首次配置、退出 5 s 预算 | 需要带模块的测试包（见阶段二） |

- **代理侧准备**：按 `docs/用户功能测试单.md` 生成一份 v0.1.0 专用勾选清单，附每项的预期读回；收集用户反馈后按问题开修复任务。
- **完成标准**：清单逐项有结论（通过 / 失败 + 证据）；失败项都有对应修复任务。

## 阶段二：Device Center 模块收口（主代理 + 用户决定，约 1 天）

- **用户决定**：DeviceCenter 仓库的合并方式（把主仓库工作区的 0.1.1 改动先提交，再合 `cli/dc-headless-ipc`；或直接采用 `cli/dc-ipc-ui-integ`）。
- **合并后**：用 `scripts/Build-TestPackage.ps1` 出完整包（控制台 + 模块）；确认模块许可证和源码归档齐全后，把模块作为第二个附件上传到 GitHub Release。
- **完成标准**：DC 主分支包含 headless IPC；完整包通过阶段一 1.4。

## 阶段三：软件温控曲线验收与收尾（Codex 修复 + 用户实测，约 2–3 天）

- **实测场景**：长时间运行（≥ 2 h）、手动停止、控制台退出、睡眠/唤醒、插拔电源，每个场景都要确认风扇回到预期状态。
- **代理侧**：把这些场景补成离线模拟测试（时钟与电源事件用假实现），确保失败路径都会恢复。
- **完成标准**：模拟测试全过；用户实测记录入 `evidence/`；README 功能表中这一行改为“本机已验证”。

## 阶段四：精确功耗（只读 → 写入，用户逐项批准，约 1 周）

1. **只读**：用户接上 U 盘后，先只读识别介质，再请用户确认部署方案；验证 GPU 只读桥，界面增加只读的 CPU/GPU 功耗显示（未知显示“—”）。
2. **写入设计**：先写契约（范围、上下限、恢复、退出与睡眠行为），用户确认后再实现；CPU PL1/PL2 与 GPU 分开推进。
3. **完成标准**：每一项写入都经用户单独批准并实测；强模型审查通过（涉及硬件写入）。

## 阶段五：外设二期（按需选择，每项约 2–4 天）

外设页“即将支持”中的四项，建议顺序：

1. **鼠标性能项**（抬升高度、静默高度）：与现有 DPI 写入路径同构，风险最低。
2. **小米云登录**：免手填 Token；涉及账号凭据，需安全审查（`/security-review`）。
3. **键盘按键层**、**鼠标宏**：要新的编辑界面，并扩充 IPC 协议 minor 版本；先出预览稿，经用户确认后再实现。

每一项都按 `docs/代理协作.md` 走：协议升 minor → Codex 实现 → 强模型审查 → 用户实测。

## 阶段六：持续项

- **资源占用对比**：在相同条件下比较本程序与厂商套件的内存、CPU 唤醒和进程数，脚本是 `scripts/Measure-Resources.ps1`，结果写进 README。
- **样式清理**：删除 `tokens.css` 中已无引用的旧兼容类，删除前先用 grep 确认。
- **自定义模块**：只保留接口文档（`docs/自定义模块接口-草案-v0.md`），有真实需求时再实现。

## 近期建议

先做阶段一的 1.1–1.3，同时请用户决定阶段二的 DC 合并方式；阶段二完成后再做 1.4。阶段三可以和阶段二并行，因为二者不碰同一硬件。
