# 授权生命周期诊断 · 2026-11-03

状态：仅诊断与方案比较，未批准实施。此次只读源码并读取微软官方文档，没有运行授权、设备查询、硬件命令或原生窗口操作，没有读取用户凭据、实际注册表配置或修改产品代码；本文件是唯一新增文件。

## 结论

当前“授权设备访问”是 **Windows UAC 提升 helper + 当前桌面进程专属 IPC 会话**，不是登录账号后取得的可续期令牌。前端没有持久的 authorized 状态；Rust 的 BrokerClient、随机管道名和 helper 进程句柄只存在于内存。真正退出桌面进程后会话自然结束，新进程没有重新连接旧 helper 的协议。

**关闭到托盘与退出后重开不同：** 前者保留桌面进程及 BrokerState，重建 WebView 正常应复用原 helper；后者初始化 BrokerState=None，需要新的提权流程。默认 close_to_tray=false，普通关闭可走真正退出。此次没有读取用户已保存设置或记录实际 PID，因此不能将用户这次“关闭重开”直接归类为其中一种。

只增加“曾授权”文件或 Credential Manager 记录不能恢复 Windows 提权。启动时可以静默检测已有会话，也已存在不提权的只读查询路径；它们只能发现当前权限/连接，不能从普通进程凭空获得管理员权限。

## 1. 点击授权时发生什么

| 层次 | 当前事实与精确位置 |
| --- | --- |
| 前端入口 | `apps/desktop/src/App.svelte:397`，authorizeDevice：显式点击后调用 api.authorizeDevice，再并行 readCapabilities/readSnapshot；仅这些读回恢复后才显示连接完成，授权返回本身不保证硬件可用。 |
| IPC 命令 | `apps/desktop/src/lib/api.ts:98-113`，command/authorizeDevice：调用 Tauri authorize_device，没有传入密码或持久令牌。 |
| Rust 会话 | `apps/desktop/src-tauri/src/main.rs:24-37`，BrokerState/authorize_device：锁住 Option<BrokerClient>，先清空旧 slot，再 launch_user_initiated，成功后存回；取消或失败不会保留旧 slot。这里只创建进程会话，没有保存授权标记。 |
| UAC | `crates/acer-broker/src/platform.rs:94-116`，launch_sta：定位主程序旁 acer-helper.exe，系统 RNG 生成 16 字节 nonce，构造含桌面 PID/nonce 的管道名，ShellExecuteExW verb=runas 启动 helper，并验证 helper 已提升。UAC 是否表现为同意框/凭据框由账号、令牌和系统策略决定，本轮未触发确认。 |
| 同用户限制 | 同文件 identity/same_user，66-82、113-115：检查 SID、登录 Session ID 和 helper elevation。不同账号凭据提权会被当前协议拒绝，不支持简单改为另一管理员账号运行。 |
| helper | `crates/acer-broker/src/main.rs:2-6` → run_helper → platform::serve；`platform.rs:168-183`：只接收固定 client-pid/nonce 参数，保留原客户端进程句柄，要求同 SID/session 且自身 elevated，创建 Verified 策略设备后服务 RPC。 |
| 逐次鉴别 | `platform.rs:141-164, 174-218`：管道 ACL 限当前用户与系统/管理员；客户端校验服务器 PID/同 SID/session/已提升；服务端核对客户端 PID/同用户，校验协议版本和递增请求 ID。nonce 用于命名/隔离，不是跨进程重启可续期的授权凭证。 |
| 操作范围 | `crates/acer-broker/src/lib.rs:18-34,69-82`，Request/Operation/BrokerClient::call：固定枚举与 deny_unknown_fields；请求/响应 ID 匹配，无通用 shell/任意 WMI 函数接口。后续方案也应保留这些边界。 |

微软将 access token 定义为进程/线程安全上下文的系统对象；UAC 为需要管理员令牌的应用建立提升上下文。应用自定义 nonce、字符串或已保存密码并不等同于该系统对象。[Access tokens](https://learn.microsoft.com/en-us/windows/win32/secauthz/access-tokens)、[UAC 工作原理](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/user-account-control/how-it-works)。

## 2. 保存在哪里，为什么会丢失

| 位置 | 已核实保存内容 / 生命周期 |
| --- | --- |
| 前端内存 | App 的 snapshot/capabilities/errors；permissionNeeded 由权限状态及错误文本推导（App.svelte:130-150），vendorAuthorized 由可读状态推导（184-189）。它们不是独立、准确的 broker 会话凭证。WebView 销毁后重置，再靠初始查询重建。 |
| Rust 内存 | main.rs:24、175 的 BrokerState 初始为 None；BrokerClient 持有 Session、递增请求 ID 和锁（lib.rs:36-40）。Session 只有管道名、helper 句柄、锁（platform.rs:84）。 |
| 配置文件 | `crates/acer-system/src/lib.rs:34-41,49-75`：app_config_dir/settings.json 只有 theme、poll_interval_ms、close_to_tray、restore_on_exit。默认 close_to_tray=false。`rules_runtime.rs:18-28` 的 rules.json 只保存规则配置，不保存提升能力。 |
| 注册表 | `crates/acer-system/src/startup.rs:4-5,31-53`：HKCU Run 的 AcerConsole 项保存登录启动命令，不是管理员授权。未读取用户当前注册表值。 |
| 凭据库/浏览器存储 | 在本次相关路径（desktop/src、src-tauri/src、acer-broker/src、acer-system/src）没有检索到 localStorage/sessionStorage/IndexedDB、CredRead/CredWrite、CryptProtectData/CryptUnprotectData 的授权持久化实现。此为限定源码范围的结论，不等同于扫描整台电脑凭据库。 |

完整退出时，客户端进程内存消失；helper 在等连接时检查被绑定的客户端进程是否仍活着，客户端退出则返回（platform.rs:194-196）。新桌面进程即使找到旧管道也不是原 PID；服务端会拒绝（208-210）。当前没有从文件重建 Session 或跨进程接管 helper 的入口。

### 两种关闭路径

1. **close_to_tray=false 且非 --tray 启动**：TitleBar 调用 Window.close；窗口关闭后主事件循环接受退出，若启用恢复则先通过 exit_bridge::attempt 处理，再退出。参见 main.rs:182-188、exit_bridge.rs:10-29。恢复失败可阻止退出并重开窗口，不能把这种场景等同于已经退出。
2. **close_to_tray=true 或 --tray 启动**：main.rs:186 在无显式退出码时 prevent_exit，主进程与 BrokerState 留存。窗口可以已经销毁；tray.rs:23-33 的 open 只重建 main WebView，不初始化应用状态。单实例再次启动也调用 tray::open（main.rs:174）。这条路径正常不应仅因窗口重建再次 UAC。
3. **托盘菜单“退出”**：tray.rs:56 使用 app.exit(0)，不符合 code.is_none 的保留条件；恢复流程允许时真正退出，会丢失本进程授权会话。

## 3. 同一进程为何也可能出现重新授权提示

- **helper 有 60 秒空闲期限**：platform.rs:192-206；每次处理后重新建立等待连接的期限，设备操作超时也可终止 helper（221）。不是账号凭据的过期时间。
- **无窗口托盘态已有心跳保护**：rules_runtime.rs:50-55 每 25 秒在规则开启、待恢复或 main 不存在时调用 keep_alive；因此不能简单声称“关闭界面停止轮询，helper 必定 60 秒后死掉”。正常无窗口路径本来就会保活。
- **隐藏/最小化但窗口仍存在的潜在缺口**：前端 schedulePoll 在 document.hidden 时跳过查询（App.svelte:486-492），而托盘心跳条件是 main 不存在。若窗口仍存在、规则未开启、无待恢复收据，源码允许出现无心跳且超过 60 秒的情形。该路径尚未现场复现；PowerWatcher 启动失败也会让整个规则/保活线程提前返回（rules_runtime.rs:32）。
- **死亡会话被清空且不会自动重新提升**：get_snapshot/get_capabilities 对 is_alive=false 或探测出错时清空 slot（main.rs:45-68）；活进程但 IPC 不可达可直接报错，不自动 runas。
- **“提示重新授权”不等于拿到了精确会话故障原因**：App 使用权限文本与 broker/pipe/transport 正则共同推导 permissionNeeded；helper 崩溃、管道超时、WMI AccessDenied 都可能映射到这条提示。没有本次 PID/错误序列，不能选定唯一根因。
- **另一代码边界**：get_snapshot/get_capabilities 先调用本地 device(&state)?，然后才选择已有 broker（main.rs:46、63）。如果本地 Device::connect 本身失败，会提前返回而不尝试已存在的 helper。此为可读出的控制流风险，不是本轮已证实故障。

## 4. 启动可否静默只读探测

**可以，而且当前前端挂载就会 refresh(true)**（App.svelte:620-643）；refresh 同时调用 get_snapshot/get_capabilities（450-478）。后端已有 broker 则尝试复用；没有 broker 则使用 Device::connect 默认 ReadOnly（acer-device/src/lib.rs:24-35）。这条路径不调用 runas，但只读 WMI 在普通权限下仍可能拒绝访问，不能保证获得完整指标或写权限。

可供后续设计选择的探测层级（本次均未执行）：

| 层级 | 可判断什么 | 不能据此判断什么 |
| --- | --- | --- |
| 当前 BrokerState + is_alive | 当前持有的 helper 进程是否尚存；is_alive 只 GetExitCodeProcess（broker/lib.rs:58-62、platform.rs:85-89），无硬件 I/O、无提权。 | 不能证明管道/设备可用，也不能跨新进程找回已丢失的 Session。 |
| 已有会话 Ping | keep_alive 走固定 Ping/Pong，确认当前认证 IPC 可应答（lib.rs:57、platform.rs:218）。 | 不能证明所有 WMI 控件可用；不能在不存在 helper 时创建权限。 |
| Snapshot/Capabilities | 实际只读读取并判断权限、设备/型号能力。 | 不应把能读取指标解释为所有写命令获准。ReadOnly 与 Verified 的写策略不同（acer-device/src/platform.rs:90-103）。 |

任何静默启动探测都应和“创建 elevated helper”分开表示；缺会话、helper 死亡、连接超时、读取权限受阻应保留区别。持久标记只能表达用户偏好/曾经的选择，不能替代上述实际探测。

## 5. 方案比较（均未批准实施）

| 方案 | 能解决的范围 | 提权范围与调用方限制 | 适用性/风险 |
| --- | --- | --- | --- |
| 持久标记 + 只读探测 | 减少误报；识别已有托盘会话并复用。 | 标记不带系统权限，不据此执行写入；只用当前会话的存活/Ping/读回证据。 | 改动最小，但不能让真正新进程无 UAC 获得当前 Verified helper。不能标记=true 就自动 runas 并称其“静默授权”。 |
| 主程序 manifest requireAdministrator | 每次启动提升整个主程序，普通启动时通常会走 UAC。 | UI/WebView/所有主进程功能一同提升，范围明显大于当前 helper。 | 不提供跨启动的“一次同意永久授权”；扩大不必要的高权限 UI 攻击面。若只给 helper 设置清单，仍要启动它、建立新会话，未解决持久问题。 |
| 一次注册的固定计划任务 | 管理员事先注册高权限动作后，可按选定登录/运行级别启动固定 broker，减少后续 runas。 | TASK_RUNLEVEL_HIGHEST 取决于任务主体，不等于自动变 SYSTEM；限制任务执行/修改 DACL，固定受保护 EXE/参数，普通调用者不能改动作或借参数运行任意命令。 | 可以作为个人机器部署选择，但当前 helper 固定 client-pid/nonce 且同 SID/session，并非可直接放进任务就复用；需要新的会合与鉴别协议。跨会话/账号任务会与现协议不兼容；更新、登录策略和任务凭据需设计。 |
| 一次安装的专用 Windows 服务 | 将长期存在的最小特权 broker 与可重启的普通 UI 分开，适合稳定支持跨进程连接。 | 安装/升级/卸载需管理权限；服务身份权限应按设备需要限制，不默认授予整个 UI 管理员能力。服务控制 DACL 与 IPC DACL 是不同边界，IPC 仍要验证连接者 SID/session/PID/受保护调用者身份、固定操作和请求格式。 | 服务通常在 Session 0；当前 same_user 的 SID/session 相等条件不能原封不动沿用。需处理多用户、设备状态所有权、限流、退出恢复、版本/升级和崩溃恢复。不是一次小 UI 修复。 |
| Windows Credential Manager 保存“令牌” | 可存应用自己发行的密钥/会话秘密，给已设计好的长期 broker 做附加身份机制。 | Credential Manager 存用户 credential set 内容；不会发行管理员 access token，也不能让普通进程恢复已失效的进程 HANDLE/Windows 提权上下文。 | 对当前 PID/nonce 会话不适用，保存 nonce 仍被 PID/session 检查拒绝。保存管理员密码并自行登录会扩大凭据暴露及生命周期管理范围，不是“记住 UAC 同意”的等价实现。不应采用其作为本问题的直接修复。 |

系统依据：[manifest 执行级别](https://learn.microsoft.com/en-us/windows/win32/sbscs/application-manifests)、[任务安全上下文/RunLevel/DACL](https://learn.microsoft.com/en-us/windows/win32/taskschd/security-contexts-for-running-tasks)、[服务安全与访问权](https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights)、[CredWriteW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credwritew)。上述为官方机制加本项目源码的方案推导，不是实装结果。此次未从产品二进制证明其实际 manifest 执行级别，也未读取当前 UAC/任务/服务策略。

持久高权限机制还需注意当前实现的边界：platform.rs 校验了 PID、SID、会话和 elevation，但没有在这些函数内完成调用方/被提权 helper 的签名或映像哈希鉴别。安装长期高权限入口时应把 EXE/配置放到普通调用者不可替换的位置，并把客户端鉴别与固定 RPC 一同设计；单靠“某用户知道管道名/密钥”不足以定义长期特权边界。

## 6. 汇报后再决策

若需求只是“关闭到托盘后重开不要反复授权”，先确认当时桌面 PID 是否保留、实际 close_to_tray/--tray 分支、helper 生存与错误；优先解决同进程复用/保活/提示归因问题。若需求明确为“真正退出、重启或登录后也不再 UAC”，需要在计划任务与长期服务等部署方案之间单独选择，不能靠持久标记或 Credential Manager 获得该能力。

本次不执行以上方案，也不将任何提权部署视为已获授权。待主对话向用户汇报实际诊断、明确所需生命周期后，再另行确定实施范围。
